# Rotating Secrets Across 50+ Services with HashiCorp Vault — Without Downtime

At The QA Company, I deployed HashiCorp Vault for secrets management and rotated credentials across more than 50 services with zero downtime. Installing Vault was the easy part. The hard part was changing how every one of those services got its credentials, while they kept serving traffic.

This post covers the decisions that made it work: which secrets should be dynamic and which should stay static, how pods authenticate to Vault, how secrets reach the application, and the order we rolled the change out in.

## Dynamic vs Static Secrets

This is the first decision for every credential, and it determines everything after it.

**Dynamic secrets** are generated on demand. When a service asks Vault for database access, Vault creates a brand-new database user with a lease (for example one hour), hands it over, and deletes the user when the lease expires. No two pods share a credential, and nothing long-lived exists that could leak.

**Static secrets** are values Vault stores but doesn't generate, such as third-party API keys, webhook signing secrets, or a license key. Vault keeps them in the KV v2 engine with versioning, but rotating them still means asking the upstream provider for a new value.

There is a middle ground, **static roles**, where Vault owns an existing database user and rotates its password on a schedule. That's useful for legacy apps that can't handle a changing username.

| Secret type | Use for | Rotation |
|-------------|---------|----------|
| Dynamic (database engine) | PostgreSQL/MySQL access from services | Automatic, per lease |
| Static role (database engine) | Legacy apps tied to one DB user | Automatic, on `rotation_period` |
| KV v2 | Third-party API keys, signing secrets | Manual or scripted, versioned |

Our rule of thumb: **if Vault can generate it, make it dynamic.** Anything else goes in KV v2 with an owner and a rotation runbook.

## Setting Up the Database Secrets Engine

```bash
vault secrets enable database

vault write database/config/orders-db \
  plugin_name=postgresql-database-plugin \
  connection_url="postgresql://{{username}}:{{password}}@orders-db.internal:5432/orders" \
  allowed_roles="orders-rw" \
  username="vault_admin" \
  password="initial-password"

# Rotate the root credential immediately so only Vault knows it
vault write -force database/rotate-root/orders-db

vault write database/roles/orders-rw \
  db_name=orders-db \
  creation_statements="CREATE ROLE \"{{name}}\" WITH LOGIN PASSWORD '{{password}}' VALID UNTIL '{{expiration}}'; GRANT orders_app TO \"{{name}}\";" \
  default_ttl=1h \
  max_ttl=24h
```

Two details that bite later:

- **Grant a group role, not table privileges.** `GRANT orders_app TO "{{name}}"` keeps the permissions in one place inside PostgreSQL. It also helps with object ownership. If a dynamic user creates a table, dropping that user later fails. Run migrations under a dedicated, stable role, not under dynamic credentials.
- **`rotate-root` means Vault is the only holder of the admin password.** That's the goal, but make sure you have a break-glass path to the database before you run it.

## Kubernetes Auth: No Secret Zero

A pod needs some identity to log in to Vault. Shipping a Vault token inside the pod would just recreate the problem. The Kubernetes auth method uses the pod's **service account token** instead, which Kubernetes already issues:

```bash
vault auth enable kubernetes

# When Vault runs inside the cluster, it can use its own service account to talk to the API
vault write auth/kubernetes/config \
  kubernetes_host="https://$KUBERNETES_SERVICE_HOST:$KUBERNETES_SERVICE_PORT"

vault policy write orders - <<'EOF'
path "database/creds/orders-rw" {
  capabilities = ["read"]
}
path "secret/data/orders/*" {
  capabilities = ["read"]
}
EOF

vault write auth/kubernetes/role/orders \
  bound_service_account_names=orders \
  bound_service_account_namespaces=prod \
  policies=orders \
  ttl=1h
```

## Getting Secrets Into Pods: Injector, CSI, or VSO

There are three supported ways for a pod to consume Vault secrets. Which one you pick decides how rotation reaches the application.

### Vault Agent Injector

A mutating webhook adds a Vault Agent sidecar to annotated pods. The agent logs in, renders secrets to files on a shared in-memory volume, and **renews and re-renders them when they change**:

```yaml
spec:
  template:
    metadata:
      annotations:
        vault.hashicorp.com/agent-inject: "true"
        vault.hashicorp.com/role: "orders"
        vault.hashicorp.com/agent-inject-secret-db: "database/creds/orders-rw"
        vault.hashicorp.com/agent-inject-template-db: |
          {{- with secret "database/creds/orders-rw" -}}
          postgresql://{{ .Data.username }}:{{ .Data.password }}@orders-db.internal:5432/orders
          {{- end }}
    spec:
      serviceAccountName: orders
```

The file shows up at `/vault/secrets/db`. This is the best fit for dynamic secrets, because the agent handles lease renewal for you.

### Secrets Store CSI Driver

The Vault CSI provider mounts secrets as a volume through a `SecretProviderClass`. There's no sidecar, which is lighter. But rotation depends on the CSI driver's rotation feature being turned on, and it can't renew leases the way the agent does, so it suits static KV secrets better than dynamic ones.

## Making the Application Rotation-Safe

Vault can rotate a credential in a second. Whether that causes downtime depends entirely on the application. Every service had to meet one of these contracts before we switched it over:

1. **Re-read on change.** The app watches the rendered file, or re-reads it when a connection fails, and rebuilds its connection pool. This is the best option.
2. **Reload on signal.** The agent can run a command after rendering via `vault.hashicorp.com/agent-inject-command-<name>`, for example sending `SIGHUP` to the app. Signalling across containers requires `shareProcessNamespace: true` on the pod.
3. **Restart on change.** For apps that only read config at startup, a rolling restart (from VSO or your own controller) swaps pods one at a time behind the Service. That only works if replicas > 1 and readiness probes are correct.

The classic failure is a connection pool that outlives the credential. A pool opens connections with a dynamic user, the lease hits `max_ttl`, Vault drops the user, and existing connections start failing. Set the pool's maximum connection lifetime **shorter than the lease TTL**, so connections recycle naturally onto the new credential before the old one disappears.

## Rotating Static Secrets Without Downtime

Dynamic secrets rotate themselves. Static secrets need a sequence that never leaves a moment where the only valid value is one some consumer doesn't have yet. The pattern is **overlap, switch, revoke**:

1. **Create** a second valid credential upstream (most providers allow two active API keys).
2. **Write** it to Vault as a new KV version: `vault kv put -mount=secret orders/payment-api api_key=<new>`.
3. **Roll** consumers onto the new version and watch error rates.
4. **Revoke** the old credential upstream, only after every consumer is confirmed on the new one.
5. If anything breaks before step 4, `vault kv rollback -mount=secret -version=<n> orders/payment-api` brings the old value back, and it's still valid upstream.

Skipping straight from step 1 to step 4 is how a "simple key rotation" turns into an incident.

## Rollout Order Across 50+ Services

We didn't migrate 50+ services at once. The order mattered as much as the mechanism:

1. **Inventory first.** List every secret, who consumes it, and whether it can be dynamic. You will find secrets nobody knew existed.
2. **Dev, then staging, then prod.** Each service runs on Vault in dev and staging for a while before its production credentials move.
3. **Least critical first.** Internal tools and batch jobs first, customer-facing paths last. The early services shake out the templates and the runbook.
4. **Consumers before revocation.** For any shared credential, move every consumer to Vault before the old value gets revoked.
5. **Short TTLs only after it's stable.** Start with generous lease TTLs, and shorten them once you trust renewal and pool recycling.

## Running Vault Itself

Vault becomes a dependency of every service, so treat it like one: run it in HA with integrated storage (Raft), auto-unseal it with a cloud KMS so a restart doesn't need humans holding unseal keys, enable an audit device from day one, and alert on lease counts and auth failures.

## Final Thoughts

Zero downtime didn't come from Vault. It came from three decisions made before any credential changed: dynamic wherever possible, applications that tolerate a credential changing under them, and a rollout order that put the riskiest services last.

If you're starting out, move one non-critical service end to end, with dynamic database credentials, Kubernetes auth and the agent injector, and write down everything that surprised you. That document becomes the runbook for every service after it.
